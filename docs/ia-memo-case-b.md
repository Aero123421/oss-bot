# IAメモ（暫定採用：案B｜Slack感触＋エージェントOS）

比喩：**AI版のSlack**（コピーはレイアウト／アイコンではなく感触）
ゴール：会話がホーム。管理画面感・Mission Control多パネルを殺す。Open WebUIに見えない。

---

## 1. 感触の原則（実装前に守る）

1. **会話がOSの正面** — 起動直後は「話す場所」。ダッシュボード／設定ツリーが先に来ない
2. **Botは名簿ではなく同席者** — モデル切替UIにしない。在席・動き・@で「誰が今いるか」が分かる
3. **重い操作はストリームに刺さる** — 承認・接続・ルーチンはAdmin逃げせず、会話上の一手（カード）
4. **場所で仕事が分かれる** — Slack同様、チャンネル（ルーム）とDMで文脈が分かれる
5. **本流を汚さない** — 長い調査・差分は脇（スレッド／展開）。ルーム本文は流し読みできる

禁止線：
- サイドバー＝設定ツリー
- Bot切替＝ドロップダウン名簿
- ストリーム＝ログビューア
- ホーム＝RAGボックス／モデルピッカー

---

## 2. 写像（Slack → 自プロダクト）

| Slack | 自プロダクト | 備考 |
|--------|--------------|------|
| ワークスペース | デプロイ／テナント | セルフホスト1インスタンス想定 |
| チャンネル | Group（ルーム） | 部門・テーマの共有仕事場 |
| DM | 1:1（ユーザー↔Bot） | 私的な窓口 |
| メンバー | Bot（役割付き） | モデル名ではなく役割名 |
| 窓口的な人 | 参謀（など） | 振り分け入口のDM |
| 未読／Activity | 要対応 | 承認・@・ルーチン完了を優先 |
| スレッド | 深掘りスレッド | 人間↔特定Bot、または長文結果 |
| Apps / Integrations | コネクタ・ルーチン・コンピュータ | 第2層。サイドバー主役にしない |

---

## 3. 画面構成（案B）

### 3.1 サイドバー（第1層ナビ）
- **ルーム（チャンネル）** — 参加中のGroup
- **DM** — 各Botとの1:1（**Dispatcher＝参謀を窓口として上位固定**）
- セクション分けは可（例：部門ルーム／個人DM）。**設定項目は置かない**
- 未読バッジ：通常新着 ＜ **要判断／要承認**（後者を視覚的に強く）

### 3.2 中央ストリーム（ホーム）
- ルームまたはDMの会話本文
- **在席表示**はヘッダ必須（誰が参加し、誰が今動いているか）
- 並列応答はストリーム上で「誰の発言か」が常に分かる（アバター／役割ラベル）
- 承認カード・コネクタ接続・ルーチン提案は**インラインカード**（別画面に飛ばない）

### 3.3 スレッド（脇）
- 用途：長い調査結果、差分比較、特定Botとの深掘り
- ルーム本流には要約または「スレッドあり」チップのみ
- スレッド未読は Activity／要対応に集約（本流を全部赤くしない）

### 3.4 要対応（Activity相当）
- 中身の優先順：①承認カード ②自分宛@ ③ルーチン完了／失敗 ④その他メンション
- 「全部の新着ログ」にしない。トリアージ用

### 3.5 第2層（会話から1タップ）
- コネクタ、ルーチン、コンピュータ、設定
- 到達経路：会話内カード／ヘッダの「…」／コマンド（`./doctor` 等はCLI）
- **常時マルチパネル化しない**

## 4. 画面優先順位（実装・レビュー用）

1. 今動いているBotの気配（在席／実行中）
2. ルームの流れ（ストリームの読みやすさ）
3. 承認カード（インライン）
4. 履歴・未読
5. （最後）設定・管理

## 5. 初回体験との整合（他部門メモとの接点）

- チュートリアルは管理画面ツアー禁止 → 「DMで話す → ルームで並列 → 承認1回 → ルーチン1本」
- `./up` 成功条件＝ブラウザが開き、自分用Botに話せる
- UI上も同じ：起動直後の着地は**自分用BotのDM**（ダッシュボードではない）

---

## 6. 受け入れ条件（GO後の実装指針）

実装・レビューは次を満たせば案B準拠：

- [ ] 初回着地が会話（DMまたはルーム）である
- [ ] サイドバーに設定ツリーがない
- [ ] Botが「モデル一覧」ではなく役割付きメンバーとして見える
- [ ] ルームヘッダに在席／実行中が分かる
- [ ] 承認がモーダル地獄やAdmin専用画面ではなくストリーム／要対応にある
- [ ] 長文結果が本流を埋め尽くさない（スレッドまたは折りたたみ）
- [ ] コネクタ／ルーチンが「初回から会話の一手」として発見できる

- [ ] Botに Ready／未ログインが区別できる
- [ ] AuthGate未設定時は専用空状態（空ホーム禁止）
- [ ] doctor／Setupが会話または空状態から辿れる
- [ ] 秘密の生値がUIに出ない（状態表示のみ）
- [ ] Dispatcher（参謀）がDM窓口として強調されている

非ゴール：
- Mission Control型の多パネル運用ダッシュボード
- Open WebUI風のモデル／知識がホームの総合チャット

## 7. BYO / AuthGate / 資格情報（プロダクト必須）

**BYO（Bring Your Own）**：モデルやAPIを同梱しない。利用者の CLI／キー／ログインをホスト側で持ち、ランタイム（Bot）へ橋渡しする。

### Bot状態（DM一覧・ヘッダで見せる）

| 状態 | 意味 | UI |
|------|------|-----|
| `Ready` | 仕事を受けられる | 通常表示。薄い在席の「動ける」 |
| `未ログイン` | BYO資格情報が未設定／失効 | バッジ「未ログイン」。会話開始前に Setup へ |
| `Setup中` | doctor／接続ウィザード進行中 | 進行表示。送信は抑止可 |
| `障害` | doctor 赤・実行失敗 | 「doctorへ」リンク。Adminツリーに逃がさない |

### AuthGate（未設定の空状態）

- 共有トークン（例: `OSS_BOT_TOKEN`）未設定時は**会話ホームを空で出さない**
- 空状態コピー例：「ワークスペースに入るにはセットアップが必要です」＋ 主CTA `./doctor` または Setup、副CTA ドキュメント
- 設定ツリーやモデルピッカーを空状態の主役にしない

### Setup / doctor 導線

- UIの修復入口は常に **doctor（何が赤か／直す1コマンド）** に収束
- 初回パス：AuthGate通過 → 自分用Bot DM（Readyまたは未ログイン明示）→ ルーム
- doctor失敗はストリームまたは要対応の承認／修復カードで返す（ログダンプ画面にしない）

### ホスト → ランタイム資格情報ブリッジ（一文）

ホスト上の BYO 資格情報はランタイムへブリッジして利用する。**UIは接続状態（Ready／未ログイン／失効）だけを表示し、トークンや秘密の生値は絶対に出さない。**

### Dispatcher（窓口）強調

- サイドバー DM で **Dispatcher（参謀）を窓口として上位固定**
- すべての送信は UI → Dispatcher（裏口でモデル／adapter直叩き禁止）
- Dispatcher は司令塔ダッシュボードではなく「最初に話しかけるDM」
